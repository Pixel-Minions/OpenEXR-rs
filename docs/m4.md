# Milestone M4: a safe Rust API (2026-11-09)

The milestone after M3 (`PLAN.md` §16, owner's decision O10): `openexr-rs` (`crates/openexr`,
library `openexr`), a crate an ordinary Rust program reads and writes OpenEXR files with,
safely, over the exact Core port. Not a port: a design, with the C++ library's names (O11),
whose every pixel and byte still comes from the Core port. No `unsafe` in the crate
(`#![forbid(unsafe_code)]`). Dependencies: `bytemuck` 1.25.2 (O14) and, behind the default
`rayon` feature, `rayon` 1.12.0 (O12).

## What it does

| Area | Types |
|---|---|
| Headers | `Header` (every attribute in the file's order, typed accessors and setters, `Header::new` with the C++ library's defaults), `Attribute` (one variant per Core attribute type, lossless), `Channel`, `TileDescription`, ... |
| Opening | `MultiPartInputFile`, `InputFile` from a path, a `Read + Seek` or bytes; `ReadOptions` (strict and silent headers, chunk table rebuilding, threads) |
| Reading | `FrameBuffer`, `Slice` (the caller's typed or byte buffers, any strides, sampling, fill values, conversion), `InputPart::read_pixels` (scanlines, tiled parts by line), `read_tiles` (any level), deep reads through `DeepFrameBuffer` (counts, then samples) |
| Writing | `MultiPartOutputFile`, `OutputFile`, `OutputPart` (`write_pixels`, `write_tile(s)` at any level and in any order, `write_deep_pixels`, `write_deep_tile(s)`), `WriteOptions` (levels, threads) |
| Whole files | `Image::read`, `Image::write` (as the Python binding's `OpenEXR.File`) |
| Threads | `Threads::{Serial, Auto, Count(n)}`: reads decode chunks in parallel straight into the caller's buffers; writes compress chunks in parallel; the same bytes either way |

## How it was checked

| Check | Result |
|---|---|
| Headers against the wheel | 1585 files (the M3 decode set: upstream's images, `write_images.py`'s layouts, the corpus, damaged copies), 20264 attributes, as the binding shows them; type names as Core's; refusals as the wheel's |
| Flat reads against the wheel | 878 parts, 7438 reads: whole, interleaved both ways, line ranges, sampled, on 1 and 4 threads; parts the wheel cannot read fail |
| Levels and conversions against Core 3.5.3 | `core_harness levels`: 6237 level-and-type reads (3363 above level 0, 147 deep), on 1 and 4 threads |
| Deep reads against the wheel | 49 deep parts, 37 line ranges |
| Writes against the wheel | Every file `write_images.py` and `write_deep.py` write (280 flat, 24 deep), from the pixels they were written from, byte for byte, on 1 and 4 threads; `Image::read` then `Image::write` (180 flat, 24 deep) |
| Writes the wheel cannot make | MIP- and RIP-mapped files, flat (30) and deep (24), tiles given in scrambled order, read back through Core 3.5.3 as written |
| `Image::read` against the wheel's `OpenEXR.File` | 698 files; 922 refused where the wheel leaves a part out |
| Platforms | Windows and Rocky Linux 9, the same counts |

## What it fixed or logged

- **I-34**: Core's uncompressed direct read ignores the line skips; the API reads part of a
  tiled part through a buffered row of tiles, as the C++ library does.
- **D-22** (I-35, W-18): Core's tile writer refused a deep tile without samples; it takes one,
  as its scanline writer does.
- The C++ library's single-part header (`type`, `name`) is restored on top of Core's writer,
  and the C++ deep writers' chunk composition is ported, quirks included.

## Speed

`docs/baseline.md`, "The safe API's speed": on one thread the API reads and writes as fast as
the C++ library or faster, but for the HTJ2K family; on 32 threads both scale, the API's less
so (`docs/deferred.md`). After M4, OpenJPH's buffers were pooled per thread and a thread
count's pool kept for the process, which took HTJ2K32 on 32 threads from 265 ms to 35 to read;
and a chunk one `write_pixels` gives whole is packed from the caller's frame buffer on the
thread that compresses it, which made the API's writes faster than the C++ library's on one
thread for every compression.

## Left for later

`docs/deferred.md`: what the C++ writer allows and Core's does not (parts in any order,
incomplete files); write conversions and an edge tile's uninitialized bytes (no oracle
reaches them); deep reads and writes on one thread; speed on many threads. Publishing (O13)
and the C++ library itself (M5) are the owner's next decisions.

## Hardening (2026-11-09)

A mutation fuzzer of every read and write path (`crates/openexr/examples/fuzz.rs`, run for
30,000 cases by `tests/heavy_fuzz.rs` on every full check; longer runs from the command line):
damaged files (bits flipped, ranges overwritten, integers planted in headers and chunk
tables, cuts, insertions) of every codec, read every way the API reads, on one thread and on
several; undamaged files read into random frame buffer layouts; random files (channels,
sampling, windows, compressions, line orders, tiles and levels, deep) written from random
layouts, those written whole read back and compared, for a lossless compression, with what
was written. About 330,000 cases run so far, Windows. What it found, fixed and kept as tests
(`tests/hardening.rs`):

- A header asking for a vast window aborted the process (an allocation of petabytes):
  every allocation the API sizes from a header is now fallible, an `OutOfMemory` error.
  `ReadOptions::max_image_size` and `max_tile_size` expose Core's own limits, for files from
  sources not trusted.
- A chunk every channel of which is sampled out packs to nothing: it is written empty, as
  Core's encode pipeline writes it, not handed to the compressor.
- A write a codec refuses part-way (OpenJPH takes sampling by powers of two only) left the
  part's lines consumed: the file is now failed, every later write and `finish` returning
  that error; a tile given twice is refused before anything is done.

The fuzzer is our own, without coverage guidance: `cargo-fuzz` (libFuzzer, nightly Rust,
the `libfuzzer-sys` dependency) would reach deeper, with the owner's OK.
